# DUOBACK React — AI 인상 점검 및 개선 시뮬레이션

작성일: 2026-10-14 · 대상: 현재 저장소의 React SPA

후속 작업: 이 문서는 수정 전 기준의 분석이다. 신뢰와 동작 범위를 먼저 정리한 결과는 [1차 개선 기록](improvement-phase-one.md)에 별도로 기록했다.

## 판단과 분석 범위

이 프로젝트에서 AI 생성물처럼 느껴질 가능성이 가장 큰 원인은 **연구소를 연상시키는 시각 표현에 비해 상품별 근거와 기능의 완결성이 부족한 것**이다. 단순히 그라데이션이나 영문을 쓰기 때문이라고 판단하지 않았다. 실제 데이터·서비스처럼 보이는 내용을 정적 예시와 미완성 동작으로 채운 부분, 의자 선택에 필요한 정보를 일반 쇼핑몰 구조에 맞춰 놓은 부분을 우선했다.

이 보고서는 AI 사용 여부나 작성자를 판별하는 문서가 아니다. 코드만으로 작성 경위를 알 수 없다. 여기서 ‘AI 인상’은 사용자가 **일반적인 템플릿에 브랜드 이름과 그럴듯한 설명을 끼워 넣었다고 느낄 수 있는 상태**를 뜻한다.

검토한 것:

- 홈, 목록, 상세, 장바구니, 브랜드, 고객지원의 소스와 데이터, 스타일, README 및 리뉴얼 문서.
- 로컬 개발 서버의 홈·목록·상세 화면, 리뷰 표시, 검색 모달과 상세 탭의 키보드 동작.
- 기본 데스크톱 뷰포트와 390×844 모바일 뷰포트. 높이는 DOM 실측값을 정수로 반올림했다.
- 제품 데이터 집계와 기존 데이터 테스트, ESLint.

README가 소개하는 별도 `DUOBACK Fit` 저장소/배포의 구현은 평가하지 않았다. `docs/renewal`은 후속 기획으로만 참고했다. 실제 제조사 자료, 인증기관, 매장 정보와 대조하지 않았으므로 출처 없는 데이터를 모두 허위라고 단정하지 않는다.

**애플리케이션 코드는 변경하지 않았다. 아래 개선 후 수치는 제안이 구현된다는 조건의 사고 시뮬레이션이며, 실제 배포 후 측정 결과가 아니다.**

## 집중적으로 발견한 문제와 제안

우선순위 P0는 신뢰를 직접 깨는 부분, P1은 선택과 탐색을 방해하는 부분, P2는 시각 및 코드 마감이다.

### 1. 모든 제품이 같은 리뷰 3개와 평점 4.8을 공유한다 — P0

근거: `src/components/product-detail/ProductTabs.jsx:32`, `:108`, `:110`, `:116`; `src/data/products-data.js`의 `reviewCount`.

제품이 바뀌어도 김**, 이**, 박**의 리뷰 본문·날짜가 그대로다. 각 제품의 리뷰 수는 다르며 합계는 598개지만, 저장소에는 공통 본문 3개만 있다. 서버에서 리뷰를 조회하는 구현은 없다. 4.8이라는 숫자 옆에 채워진 별은 4개라 표시도 맞지 않는다. 리뷰에는 통증이 없어졌다는 표현도 있어, 예시임을 밝히지 않은 상태에서는 신뢰할 만한 후기처럼 읽힌다.

**개선:** 실데이터가 없으면 고객 리뷰·평점·리뷰 수를 숨긴다. 인터랙션 시연이 필요하면 ‘예시 리뷰’라고 탭과 본문에 표시하고 실제 구매자 통계처럼 집계하지 않는다. 실제 리뷰를 도입할 때는 제품 ID별로 연결하고 같은 원천 데이터에서 본문·개수·평점·별을 계산한다. 자연스러운 말투의 가상 리뷰를 더 만드는 방식은 문제를 키운다.

**예상 효과:** 다섯 제품에서 발생하는 리뷰 신뢰 문제를 함께 해소한다. 다만 숨기는 것만으로 실제 고객 근거가 생기는 것은 아니다.

### 2. A/S가 전송 없이 ‘접수 완료’를 알린다 — P0

근거: `src/pages/Support.jsx:58`.

제출 함수는 `preventDefault()`와 `alert()`뿐이다. 접수 저장·전송·번호 발급이 없는데 담당자가 연락할 것이라고 알린다. 입력 폼은 이름·전화·이메일·구매일·증상을 요구해 실제 서비스처럼 보인다.

**개선:** 폼을 유지한다면 입력 전에 ‘A/S 신청 화면 시연이며 입력 내용은 전송되지 않습니다’를 표시하고, 제출 결과도 ‘입력 확인 완료’로 맞춘다. 실서비스로 만들 경우에는 서버 응답으로 접수 성공을 확인한 뒤 접수 번호를 보여준다. 데모에서는 개인 연락처를 입력하도록 유도할 필요도 없다.

**예상 효과:** 거짓 접수 성공 경로 1개를 제거한다. 실제 접수율 개선과는 별개다.

### 3. 결제와 구매 버튼이 구현 범위보다 크게 약속한다 — P0

근거: `src/components/cart/CartSummary.jsx:9`, `:41`; `src/components/product-detail/ProductInfo.jsx:35`.

‘바로 구매하기’는 장바구니로 이동하고, ‘결제하기’는 결제 단계 없이 장바구니를 비운 다음 데모 주문 완료를 알린다. 데모임은 행동 후에야 드러난다. 사용자가 고른 항목도 사라진다.

**개선:** 커머스 데모를 유지한다면 버튼을 ‘주문 흐름 체험’으로 표시하고, 주문 요약과 선택 내역을 유지한 결과 화면을 제공한다. 포트폴리오의 초점을 쇼룸으로 옮긴다면 구매 대신 비교·체험 매장 연결을 제공한다. 현재 요청에서 기존 장바구니를 즉시 제거하라는 의미는 아니다.

**예상 효과:** 결제에 대한 사전 오해와 장바구니 소실을 방지한다. 결제 성공률이 올라간다고 말할 수는 없다.

### 4. 인증·연혁·매장·인기도에 근거가 없다 — P0

근거: `src/data/products-data.js:58` 등 KC 값; `src/pages/Support.jsx:24`; `src/pages/Brand.jsx:44`; `src/components/home/TrustAwards.jsx:3`; `src/components/home/BestProducts.jsx:5`.

KC 값은 `KC-AB-1234-5678` 등의 연속적인 예시 형태이며 첫 두 제품은 같은 값을 쓴다. 공유 인증이 가능한지 확인한 자료가 없다. 매장 주소는 123/456/789, 전화는 1234-5678 형태다. 연혁 6개와 인증·수상 로고 4개에는 확인 링크와 적용 대상이 없다. ‘지금 가장 많이 찾는’ 제품은 하드코딩한 `popularScore`로 결정된다. 정적 숫자가 현재의 판매·검색 집계처럼 보이는 점이 문제다.

**개선:** 데이터에 출처 URL·확인일·적용 모델·예시 여부를 기록한다. 확인하지 못한 수치는 공개 화면에서 제거하거나 명확히 예시로 표시한다. 판매 집계가 없으면 ‘베스트셀러’ 대신 ‘주요 모델’로 바꾸고 선정 기준을 공개한다. 인증과 수상은 각각 적용 모델·번호·연도·발급 또는 수여 주체를 설명한다.

**예상 효과:** 연구소 같은 외관을 실제 근거가 뒷받침하게 된다. 출처 검증 전에는 사양에 기반한 정교한 추천도 신뢰할 수 없다.

### 5. 정책과 연락처가 서로 다르다 — P0

근거: `src/pages/Support.jsx:7`, `:10`, `:99`; `src/components/product-detail/ProductTabs.jsx:144`, `:158`.

명확한 불일치 두 가지가 있다. FAQ는 주문 확인 후 2–3 영업일, 상세는 결제 완료 후 2–5 영업일이라고 한다. 기준 시점도 다르지만 그 차이를 설명하지 않는다. 고객지원은 1588-1234, 상세 A/S는 1588-XXXX다. 무이자 할부 등의 정책도 출처 없이 넓게 단정한다.

**개선:** 배송·보증·연락처를 공통 정책 데이터로 관리한다. 서로 다른 기간이 의도된 것이라면 ‘출고 준비’와 ‘수령 예상’처럼 범위와 시점을 구분한다. 확인하지 못한 정책은 실서비스 조건처럼 표시하지 않는다.

**예상 효과:** 확인된 정책/연락처 불일치 2종을 0종으로 줄일 수 있다. 정합성 확보가 정책의 진실성을 보장하지는 않는다.

### 6. 다섯 제품의 상세 설명이 같은 기술을 일괄 주장한다 — P1

근거: `src/components/product-detail/ProductTabs.jsx:67–81`; `src/data/products-data.js:79`.

요약 한 문장을 제외하면 모든 모델에 ‘듀얼백 시스템’과 ‘에어 메쉬 소재’가 붙는다. ‘어떤 자세에서도 편안함’ 같은 무조건적인 문구도 공유된다. 듀얼백 설명은 ‘상부와 하부’라고 하지만, 일부 제품 사진은 좌우로 나뉜 등받이 또는 단일 메쉬 등판으로 보인다. DK-073W 사진의 고정 다리 형태와 데이터의 높이 조절·4D 팔걸이도 재확인이 필요하다. 사진만으로 실제 사양을 확정할 수는 없지만 데이터와 이미지가 맞물리지 않는 신호다.

**개선:** 제품별 `features`에 확인된 기능·설명·해당 부품 사진을 연결한다. 없는 기능의 섹션은 렌더링하지 않는다. 각 제품을 ‘이 모델을 선택할 이유 / 다른 모델을 볼 이유’로 설명하고, 단순한 제품 측면 사진을 기술 구조의 증거처럼 쓰지 않는다.

**예상 효과:** 문장 재작성보다 모델 간 차이와 데이터 정확성이 개선된다. 공통 컴포넌트는 유지하고 콘텐츠를 제품별로 나누면 된다.

### 7. 홈의 숫자가 브랜드 수치인지 제품 사양인지 모호하다 — P1

근거: `src/components/home/HeroSection.jsx:43`.

‘30+ 연구 연수’, ‘4D 조절 시스템’, ‘130kg 최대 하중’이 같은 형식으로 놓인다. 첫 값은 브랜드 설명이고 나머지는 대표 모델에 한정될 수 있다. 데이터에서는 팔걸이가 고정/3D/4D로 다르고 하중도 100/120/130kg으로 나뉜다. 4D가 어느 부품을 어떻게 조절한다는 뜻인지도 알 수 없다.

**개선:** 연구 기간은 출처가 있는 브랜드 영역으로 옮긴다. 제품 수치는 ‘D2500G-DASW 기준’으로 묶어 상세에 연결한다. 4D는 공식 확인된 조절 방향과 부품명을 풀어 쓴다.

**예상 효과:** 모든 제품에 같은 기능이 있다는 오해를 줄인다. 숫자를 더 크게 만드는 것보다 정보의 적용 범위를 분명하게 만드는 편이 유효하다.

### 8. 카피가 추상적이고 브랜드를 바꿔도 성립한다 — P1

근거: `src/components/home/HeroSection.jsx:12`; `src/components/home/BrandStory.jsx:20`; `src/pages/Brand.jsx:53`, `:79`; 제품 `summary`.

‘당신의 자세를 설계하는’, ‘몸의 균형’, ‘끊임없는 연구’, ‘인체공학·품질·혁신·지속가능성’은 제품 선택을 구체적으로 돕지 않는다. 출처 없는 철학 문구를 인용문처럼 제시한 것도 권위를 빌리는 인상이다. ‘프리미엄’과 ‘균형’은 많지만 무엇이 다른지 적다.

**개선 예시:**

- 홈 제목: ‘팔걸이와 좌판 높이, 모델별로 비교하세요.’
- 홈 설명: ‘사무용 3종과 학생용 2종의 가격·좌판 높이·팔걸이 방식을 확인할 수 있습니다.’
- CTA: 현재는 ‘모델별 사양 보기’; 비교 기능 구현 후 ‘의자 비교하기’.
- 제품 설명: ‘팔걸이 4D 조절 / 좌판 높이 450–550mm / 메쉬 소재’처럼 확인된 차이를 먼저 쓴다. 제품 데이터 검증 후 사용한다.

**예상 효과:** 브랜드 약속보다 사용자가 할 수 있는 행동이 명확해진다. 인체공학 효능이나 개인의 착좌 적합성을 수치만으로 단정하지 않는다.

### 9. 사무실 스톡 사진이 브랜드 연구의 증거처럼 사용된다 — P1

근거: `src/components/home/BrandStory.jsx:11`; `src/styles/brand.css:16`.

같은 Unsplash 사무실 사진이 홈의 ‘30년 연구’ 영역과 브랜드 히어로에 반복된다. 화면에는 듀오백의 실험·제조·실제 착좌 환경이라는 설명을 뒷받침할 정보가 없다. 사진이 AI 생성이라는 의미는 아니다. 브랜드에 특화되지 않은 소재가 문제다.

**개선:** 확인된 연구/제조/쇼룸 사진을 출처와 함께 쓰거나, 현재 보유한 제품 사진으로 조절 부위를 설명한다. 스톡을 유지한다면 분위기 이미지임을 분명히 하고 연구 근거처럼 배치하지 않는다.

**예상 효과:** 다른 가구·오피스 브랜드에도 그대로 붙일 수 있는 분위기 섹션에서 제품 고유 콘텐츠로 바뀐다.

### 10. 측정 장식과 영문 라벨이 정보보다 앞선다 — P2

근거: `src/styles/common.css:101`, `:30`; `src/styles/art-direction.css:13`, `:106`; 홈 컴포넌트들.

홈에는 영문 라벨/태그 6개, 대표 이미지의 모서리 표시 4개, 반복적인 인덱스와 선이 있다. 격자·글로우·브론즈 강조·세리프 강조가 동시에 작동한다. 실제 측정 결과나 비교 기준은 적어 ‘정밀함을 묘사한 UI’라는 인상이 생긴다.

폰트는 IBM Plex Sans KR, Space Grotesk, Newsreader로 선언되어 있지만 프로젝트에서 웹폰트를 제공하는 경로는 확인되지 않는다. 로컬 설치 여부에 따라 폴백이 달라진다. 이는 세 폰트를 의도대로 로딩한 디자인이라고 보기 어렵게 한다. 일부 한글 강조는 본문과 다른 세리프로 보였다.

**개선:** 한글 본문과 제목을 안정적으로 제공하는 글꼴을 기준으로 잡고, 숫자용 보조 글꼴은 필요한 곳만 쓴다. 컬러·대표 사진은 유지하고 격자와 측정 프레임을 줄인다. 선과 강조는 실제 비교 차이·선택 상태에 사용한다. 홈 영문 라벨은 6개 중 4개를 삭제하거나 한글 설명에 합치는 안을 제안한다.

**예상 효과:** 라벨 수 6→2, 모서리 표시 4→0은 설계상 가능하다. 그러나 요소 개수가 67% 줄었다고 AI 인상이 67% 줄었다고 해석해서는 안 된다. 단순화만 하면 특징 없는 UI가 될 수 있어 제품 고유 이미지와 설명이 함께 필요하다.

### 11. 모바일에서 부차적인 지표가 제품보다 많은 공간을 쓴다 — P1

## 사고 시뮬레이션: 무엇이 얼마나 달라지는가

### A. 모바일 홈 진입

가정: 현재의 텍스트·이미지·섹션 간격은 유지하고, 지표 영역만 439px에서 96px로 줄인다. 실제 CSS 구현 후에는 폰트와 줄바꿈에 따라 재측정해야 한다.

| 항목 | 현재 실측 | 개선안의 조건부 결과 | 계산 |
|---|---:|---:|---|
| 지표 영역 높이 | 439px | 96px | 343px 감소, 약 78% |
| 히어로 높이 | 1,219px | 876px | 343px 감소, 약 28% |
| 다음 제품 섹션 시작 | 1,280px | 937px | 약 27% 앞당김 |
| 지표 설명 글자 크기 | 10px | 12–14px 목표 | 크기 20–40% 증가; 이해도 실측 아님 |

제품 섹션은 조금 스크롤하면 만나게 되지만 첫 화면에는 여전히 들어오지 않는다. 첫 화면 노출까지 원한다면 카피 길이·CTA·사진 높이의 추가 조정이 필요하다.

### B. 제품 2–3개 비교

과업: 목록에서 시작해 같은 사무용 범주의 후보를 골라 **소재 등 상세 스펙 탭에 있는 정보**를 비교한다. 가격만 비교하는 과업에는 현재 목록으로도 충분하므로 아래 계산을 적용하지 않는다. 스크롤·읽기 시간은 제외한다.

- 2개, 목록 왕복: A 상세 → 스펙 → 목록으로 뒤로 → B 상세 → 스펙 = 5회.
- 2개, 기존 관련 제품 사용: A 상세 → 스펙 → 관련 B → 스펙 = 4회.
- 제안: A 선택 → B 선택 → 비교 = 3회.
- 3개, 목록 왕복은 8회, 관련 제품 연결은 6회. 제안은 A/B/C 선택 후 비교로 4회.

| 과업 | 현재 클릭 | 제안 클릭 | 조건부 감소 |
|---|---:|---:|---:|
| 2개 비교, 기존 관련 제품 경로 기준 | 4 | 3 | 25% |
| 2개 비교, 목록 왕복 기준 | 5 | 3 | 40% |
| 3개 비교, 기존 관련 제품 경로 기준 | 6 | 4 | 약 33% |
| 3개 비교, 목록 왕복 기준 | 8 | 4 | 50% |

동시에 비교할 수 있는 모델은 현재 1개 화면에서 제안상 최대 3개로 늘어난다. 다만 모바일 비교표가 가로 스크롤로 어렵게 읽히면 클릭 이득이 사라질 수 있다. 차이 항목과 모델 헤더를 유지하는 모바일 구성이 필요하다.

### C. 예산으로 후보 좁히기

가정: 저장소의 표시 가격을 그대로 쓰며 ‘80만원 이하’ 필터를 추가한다. 가격의 실제 판매 정확성은 검증하지 않았다.

| 조건 | 필터 전 후보 | 필터 후 후보 | 결과 |
|---|---:|---:|---|
| 전체 + 80만원 이하 | 5종 | 3종 | 검토 후보 40% 감소 |
| 사무용 + 80만원 이하 | 3종 | 1종 | 검토 후보 약 67% 감소 |

남는 사무용은 저장소 데이터 기준 D3-HS다. 이것은 예산 조건 통과일 뿐 사용자 몸에 맞는다는 추천이 아니다. 현재 낮은 가격순 정렬로도 비슷한 판단이 가능하므로, 후보 수 감소를 의사결정 효율의 순증으로 전부 계산하지 않는다.

### D. 신뢰와 기능의 완결성

| 검증 항목 | 현재 | 제안 완료 시 합격 기준 | 의미 |
|---|---:|---:|---|
| 실데이터처럼 보이는 미검증 리뷰 통계 화면 | 제품 5개 | 0개 | 숨김 또는 명확한 예시 표시 |
| 전송 없는 A/S 접수 완료 경로 | 1개 | 0개 | 동작과 안내가 일치 |
| 데모 결제 과정의 장바구니 삭제 경로 | 1개 | 0개 | 체험 후 선택 내역 유지 |
| 확인된 정책/연락처 불일치 | 2종 | 0종 | 공통 데이터와 명확한 범위 |

이 값은 각 문제 경로를 없애면 달성 가능한 조건부 결과다. 신뢰도가 100% 상승한다는 뜻이 아니다. 정보를 삭제해 얻는 정합성과, 검증된 자료를 확보해 얻는 정보 가치는 별도로 평가해야 한다.

### E. 방문자와 포트폴리오 검토자의 관점

방문자가 홈에서 ‘왜 이 의자인가’를 찾는 상황에서는, 현재의 영문 라벨·숫자·브랜드 약속에서 확인된 모델 차이·비교·체험으로 시선이 옮겨갈 가능성이 높다. 포트폴리오 검토자가 리뷰·접수·결제를 눌러 보는 상황에서는, 겉보기 기능 수보다 구현 범위를 정확히 표현한 상태가 완성도를 설명하기 쉽다.

반대 시나리오도 있다. 장식만 삭제하면 평범한 쇼핑몰이 되고, 리뷰를 숨기기만 하면 구매 근거가 더 적어지며, 검증하지 않은 사양으로 Fit 점수를 만들면 그럴듯한 숫자가 하나 더 늘어난다. 따라서 **근거 정리 → 모델별 차이 → 비교 흐름 → 시각 단순화** 순서를 권한다.

‘AI처럼 보인다’ 응답 비율, 신뢰 점수, 결정 시간, 전환율의 개선 폭은 이 분석만으로 숫자를 산정하지 않았다. 사고 시뮬레이션을 실제 개선 실적으로 포장하는 것은 이 프로젝트에서 지적한 문제를 보고서가 반복하는 셈이다.

## 유지할 장점과 실행 검증

제품별 2색×4각도 이미지 참조 40개가 존재하고 기존 테스트가 이를 확인한다. 색상에 따라 갤러리를 바꾸는 구조, 공통 카테고리 데이터, 상세 상단의 핵심 사양 3개, 장바구니 수량 정규화와 저장된 데이터 파싱 예외 대응은 유지할 가치가 있다. 밝은 바탕과 그린 액센트도 원인 자체는 아니다. Next.js나 TypeScript로 바꾸는 것만으로 위의 콘텐츠·기능 문제는 해결되지 않는다.

검증 결과:

- `npm run lint`: 통과.
- 기본 `npm test`는 실행 환경의 자식 프로세스 생성 제한(`spawn EPERM`)으로 실행되지 않았다. 코드 테스트 실패로 해석하지 않았다.
- `node --test --test-isolation=none tests/data.test.mjs`: 기존 3개 테스트 모두 통과.
- 테스트 범위는 ID 고유성·이미지 파일 존재·카테고리 연결이며, 사양 진실성·리뷰·접수·결제·접근성의 정확성을 보증하지 않는다.
- 로컬 화면과 키보드 동작은 별도로 관찰했다. A/S·주문을 실제 제출하거나 기존 장바구니를 비우지는 않았다.
- 앱 소스 변경 없음. 보고서 및 집계 파일만 추가했다.
